## Acceptance fixture

Use five original modules for mission/capability, dispatch application, dispatch API, network and classified data flows. A proposed propagation path is `application.dispatch depends_on service.dispatch-api` (reverse from service to consumer), `application.dispatch realizes capability.dispatch` (forward), then `capability.dispatch supports mission.response` (forward). A second unrelated service and a cyclic pair of application dependencies exercise false positives and termination. Classification stays an authored value.

From a workspace with an unambiguous entrypoint, the proposed modified-service interface is:

```sh
arcxiom impact --changed service.dispatch-api --to mission --explain --json
```

Run a modification and a removal as separate acceptance cases. The modification returns the mission and its typed witness path. For the removal, provide a pinned pre-change baseline and identify the witness locations as baseline locations. A candidate still containing a dangling edge must separately report that invalid reference. A missing service in a candidate without baseline information cannot establish zero impact.

Qualify equivalent import-order permutations against a frozen composed graph digest. Check deterministic diagnostics for missing references, namespace collisions and invalid lock pins. Confirm every reported finding maps to the correct original file and span. Require bounded completion on cycles and explicit incomplete results on traversal-budget exhaustion.

Requirements, evidence and four-state constraint outcomes follow in v0.4.0a1. Viewpoints and loss-aware external mappings follow in v0.5.0a1. Observed-state drift and authenticated baseline promotion follow in v0.6.0a1. These are sequencing proposals. No date, public release, external adapter, remote fetch or CAD deliverable is scheduled here.
